# M5 設計：SMF → MML 変換（2026-10-25）

製品仕様は `docs/spec.md`（v0.6）。本書はその M5（「conv：SMF → MML 変換」）の設計である。M4 の設計は `docs/superpowers/specs/2026-10-23-m4-runtime-design.md`、MML の文法は `docs/mml.md`。

本書の「私の判断」は、依頼者と合意したものではなく、設計者（Claude）が決めたものである。依頼者が読んで違えば直す。「依頼者の決定」は、2026-10-25 の brainstorming で依頼者が決めたもの（設計者の案を依頼者が「提案どおりでよい」としたものを含む）である。spec §6 にすでに書いてあり、本書で変えないものは「spec のとおり」とする。

## 1. 目的と完了条件

- 目的：依頼者が DAW（Domino）で作った SMF を、ゲームでそのまま鳴らせる MML に変換する。出力した MML は手で直さずに使う想定（依頼者の決定）。そのため、読みやすさより、SMF に忠実なことを優先する。
- 完了条件（spec §7 の M5）：自作の SMF が変換・再生できる。`--report` が機能する。

### 1.1 依頼者が確かめること

公開の後、依頼者が次を確かめる。

| # | 確かめること | 確かめ方 |
|---|---|---|
| 1 | Domino の曲が変換できる | 依頼者の曲を変換し、エラーなしで MML ができる |
| 2 | 変換した曲が鳴る | 試聴ページの MML の欄に貼って「BGM 再生」で鳴らす。Domino で聞いたときと、音の高さ・タイミング・テンポが同じ（音色は違ってよい） |
| 3 | 和音とドラムが鳴る | 和音のあるパートと、ドラムのパートが欠けずに鳴る |
| 4 | 強弱が付く | ベロシティ・ボリューム・エクスプレッションの差が音量の差として聞こえる |
| 5 | ループ | `loop`・`loopend` のマーカーを入れた曲は、その間を繰り返す。入れない曲は、頭から終わりまでを繰り返す |
| 6 | `--report` | 捨てたイベントの種類と件数が出る |

テストで確かめられることは、実装側が Vitest で確かめる（§9）。

## 2. 範囲

### 2.1 作るもの

- `packages/conv`（新規）：SMF を読み、MML のテキストを書く変換と、Node.js のコマンド。
- `packages/sequencer`：ドラムのサブトラック `R1`、`R2`、… を読めるようにする（§6.10）。
- 文書：`docs/conv.md`（新規。使い方、変換の規則、警告とエラーの一覧）と、正典の更新（§10）。

### 2.2 作らないもの

| 機能 | 理由・時期 |
|---|---|
| 出力の読みやすさのための工夫（`[ ]` での繰り返しのまとめ、`l` での既定の音長の切り替え、行の折り返しの調整など） | そのまま鳴らす想定のため（依頼者の決定）。音長の書き方は §6.4 |
| 試聴ページでの SMF の読み込み（ドラッグして変換） | spec §6.1 はコマンド。依頼者から求められていない |
| ループしない曲の出力 | 依頼者の決定（§5）。変換した曲はすべてループする |
| MML → SMF の逆変換 | spec §9 の未決事項 6 のとおり後回し |
| サステインペダル（コントロールチェンジ 64 番）などの反映 | spec §6.2 の「その他」として捨て、`--report` に出す |
| コントロールチェンジやピッチベンドを曲線で描いた曲のための間引きの工夫 | 依頼者は曲線で描かない。入っていた場合は §6.5 の上限でエラーにする（依頼者の決定） |

## 3. コマンド

- `npm run conv -- song.mid -o song.mml [--quantize 32] [--report]`（私の判断。spec §6.1 の `fm-conv` は npm に公開しないため、他の道具と同じく npm のスクリプトにする）。Node.js の型を外す実行（`node file.ts`）で動かす。
- `-o` を省いたら、標準出力に MML を書く（私の判断）。
- 警告は標準エラーに出す。エラーがあれば、MML を書かず、終了コードを 0 以外にする。
- `--report`：spec §6.2 のとおり、捨てたイベントの種類と件数を出す。あわせて、トラックの割り当て（SMF のチャンネル → MML のトラック名、和音で分けた数）、ループの位置を出す（私の判断）。
- SMF の読み込みは自前で書く（私の判断。依存のライブラリを増やさない。SMF は小さく、形式が単純）。

## 4. 読み込む SMF

- フォーマット 0 と 1 を読む。フォーマット 2 と、時間の単位が SMPTE の SMF はエラー（私の判断）。
- フォーマット 1 では、全トラックのイベントを時刻順に合わせ、MIDI チャンネルごとに扱う（同じチャンネルのイベントが複数の SMF のトラックにあってもよい）。
- SMF の時刻（四分音符あたりの分解能は SMF による。Domino は既定で 480）を、MML の 96 に換えてから量子化する（§6.3）。
- ベロシティ 0 のノートオンはノートオフとして扱う。
- 同じチャンネル・同じノート番号のノートオンが、前のノートのノートオフより先に来たら、前のノートをその時刻で終える（私の判断）。

## 5. ループ（依頼者の決定）

- ループは SMF のマーカー（メタイベント）で示す。文字が `loop` のマーカーの位置を `L`、`loopend` のマーカーの位置を `E` にする。大文字・小文字は区別しない。
- マーカーがない曲は、曲の頭から終わりまでをループさせる（`L` を曲の頭、`E` を曲の終わり）。曲の終わりは、最後のノートオフを含む小節の終わり（次の小節線）とする（私の判断）。小節は SMF の拍子（メタイベント）から求め、拍子がなければ 4/4。
- `loop` と `loopend` の片方しかない、`loopend` が `loop` より前か同じ位置、どちらかが 2 つ以上ある場合はエラー（私の判断。曲の終わりやループの範囲を決められないため）。
- `loopend` の位置かそれより後のノートオンと、すべての変化（音量・ピッチベンド・テンポ・パン・音色）は、鳴ることがないので書かない。`loopend` と同じ位置の変化も含む。`parseMml` は `E` の位置かそれより後の `B v t @ p q o < > l` とノートオンをエラーにするため、`E` より後には、越えて続くノートの残りと休符だけを書く。捨てた件数は警告に出す（私の判断）。`loopend` より前にノートオンし、`loopend` を越えて続くノートは、そのまま越えて書く（ループ後も持続する。M3 の決まり）。
- 量子化（§6.3）はマーカーの位置にもかける。

## 6. 変換の規則

### 6.1 トラックの割り当て

- spec のとおり：チャンネル 1〜16 を `A`〜`P` に（チャンネル番号と同じ位置の文字。チャンネル 10 に当たる `J` は使わない）、チャンネル 10 を `R` に割り当てる。ノートのないチャンネルはトラックを作らない。
- テンポ・`L`・`E` は、休符だけの指揮用のトラック `J` に書く（私の判断）。`docs/mml.md` の規則で、タイの間には `B`・`v` しか書けないため、ノートのあるトラックに書くと、持続中のノートの途中のテンポ変更が書けない。`J` はチャンネル 10 の位置で、ノートのトラックには使われない。
- 和音・同時打ちで分けたサブトラック、`R`、`J` を含めて、トラックが 30 を超えたら、変換をエラーで止める（依頼者の決定）。エラーの文には、チャンネルごとのトラック数を出す。

### 6.2 和音（spec §6.4 の具体化）

- 1 つのチャンネルで同時に 2 音以上が鳴る区間があれば、そのチャンネルをサブトラック（`A1`、`A2`、…）に分ける。和音のないチャンネルは、分けずに `A` のまま（私の判断）。
- 持続中のノートは、途中で別のサブトラックへ移せない。そのため、新しいノートは空いているサブトラックに入れ、なるべく高い音が若い番号に来るようにする。割り当ての方法は実装側に任せる。サブトラックの数は、そのチャンネルの同時発音数の最大と同じにする。
- 音色・パン・音量・ピッチベンドは、そのチャンネルのすべてのサブトラックに書く（spec のとおり。チャンネル 10 は §6.7）。

### 6.3 量子化

- 既定は 32 分音符（12 ティック）単位。`--quantize` で 4・8・16・32・64 分音符を選べる（私の判断。96 ティックを割り切れる単位）。
- 3 連符は検出して 3 連の位置にそろえる（spec のとおり）。3 連の単位は、量子化の単位の 2/3（既定で 8 ティック）。拍（四分音符）ごとに、普通の単位と 3 連の単位のどちらにそろえたほうが、その拍のノートオン・ノートオフのずれが小さいかで選ぶ、を基本とする。方法は実装側に任せる。目標：Domino で 3 連符として打ち込んだ 8 分・16 分の 3 連符が、ずれなく 3 連の長さになる。普通の 16 分・32 分音符が 3 連に化けない。
- 量子化で長さが 0 になったメロディのノートは、量子化の単位 1 つ分の長さにし、警告する（私の判断。spec §6.7 は警告だけを決めていた。捨てると音が欠けるため）。
- ドラムのノートは長さを見ない（§6.6）。

### 6.4 音符・休符の書き方（私の判断）

- 長さは、`1 2 4 8 16 32` と 3 連の `3 6 12 24 48`（付点を含む）でちょうど表せるときはそれを使い、表せないときは `%N` で書く。どちらでも鳴る音は同じなので、細部は実装側に任せる。
- ノートの間のすき間は休符で埋める。トラックの長さは、各トラックの最後を休符で `E` の位置までそろえなくてもよい（曲の長さはいちばん長いトラックで決まる。`J` は `E` まで休符で埋める）。

### 6.5 音量（依頼者の決定）

- ノートの音量は、チャンネルボリューム（コントロールチェンジ 7 番）× エクスプレッション（11 番）× そのノートのベロシティで決め、`v` の 16 段階に丸める。依頼者は「そこまで細かい段階は要らない」とした。
- 換算（私の判断）：GM の推奨にならい、3 つの値をそれぞれ 40 × log10(値 / 127) dB とみなして足し、`v` = 15 + round(合計 dB / 3)（1 段 3 dB、`v15` が 0 dB）。3 つのどれかが 0 なら `v0`、それ以外で 1 を下回れば `v1`。ボリュームの初期値は 100、エクスプレッションの初期値は 127（GM の初期値）。
- ノートの途中でボリュームやエクスプレッションが変わったら、その位置に `v` を書く（タイの間に書ける。`v` は持続中のノートに効く）。
- 値が変わらない `v` は書かない。同じ位置（量子化の後）の変化は最後の値だけを書く。
- ドラム（`R`）も同じ換算で、ドラムごとに `v` を書く。

### 6.6 ドラム

- ノート番号の割り当ては spec §6.6 のとおり。割り当てのないノートは捨てて警告する（spec のとおり）。
- ドラムは鳴り始めたら鳴り終わるまで鳴る（M2 の決まり）ので、SMF のノートオフは見ない。MML の音長は、次のドラムまで（休符を含む書き方は実装側に任せる）。
- 同じ時刻に 2 つ以上のドラムを打つ場合（バスドラムとハイハットなど）は、和音と同じく `R1`、`R2`、… に分ける（依頼者の決定）。同時打ちのない曲は、分けずに `R` のまま。分け方（どのドラムをどのサブトラックに入れるか）は実装側に任せる。
- そのため、MML の文法を広げる（§6.10）。

### 6.7 ピッチベンド・パン・音色・テンポ

- ピッチベンド：`B` のセントに換える。ベンド幅は既定で ±2 半音、RPN 0（ピッチベンド・センシティビティ）があれば反映する（spec のとおり）。換えた値が ±1200 セントを超えたらエラー（依頼者の「許容度を超えたらエラー」に合わせた私の判断）。同じ位置の変化は最後の値だけ、値が変わらないものは書かない。
- パン（コントロールチェンジ 10 番）：`p` に換える。`p` は次の音から効くので、次のノートの直前に書く。
- プログラムチェンジ：`@` に換える（GM の番号のまま。spec のとおり）。次のノートの直前に書く。
- チャンネル 10 のプログラムチェンジとピッチベンドは捨て、`--report` に出す（私の判断。`R` には `@`・`B` を書けない）。
- テンポ：`t` に換える。BPM は小数で、曲全体のずれが聞いて分からない程度の桁に丸める（桁は実装側に任せる）。1〜999 を外れたらエラー。

### 6.8 上限とエラー

- 曲線で描いたコントロールチェンジやピッチベンドが大量に入っていても、量子化と「同じ位置は最後の値だけ」で減る。それでも MML の上限（1 トラックのイベント 10 万など、`docs/mml.md`・`parseMml`）を超えたら、変換をエラーで止める。専用の上限は作らない（私の判断。依頼者の「許容度を超えたらエラー」と、「想定外の入力への対策は過剰に扱わない」方針による）。
- 出力した MML は、必ず `parseMml` で解析し直す。エラーが 1 つでもあれば、MML を書かずに変換をエラーで止め、`parseMml` のエラーを出す（ループの中のノートが長すぎる場合なども、ここで止まる）。

### 6.9 警告

spec §6.7 のとおり：

- 同時に鳴るノートが 16 を超える箇所を、小節・拍の位置を付けて警告する（自動では間引かない）。数え方の細部は実装側に任せる。
- 量子化で長さが 0 になったノート（§6.3）。
- 割り当てのないドラムのノート（§6.6）。
- `loopend` より後で捨てたノートとコントロール（§5）。

### 6.10 MML の文法の拡張：ドラムのサブトラック（依頼者の決定）

- トラック名に `R1`、`R2`、…（`R` に 1 以上の整数。先頭は 0 でない）を足す。`A1` などと同じく、`R` とは別のトラックとして扱い、30 トラックの上限に数える。
- `R1` などは、`R` と同じドラムトラックの規則に従う（ドラム名を書く、`@`・`B`・`&`・音符・`o < >` はエラー、など）。
- 試聴ページのリズムなど、`R` という名前を特別に扱っている所があれば、`R1` なども同じく扱う。
- 手書きの MML でも使える。`docs/mml.md`・`docs/spec.md` §4.2 に書く。
- パーサーを触るので、`npm run measure:player` で 1 回の pump の最大が変わらないことを確かめる（CLAUDE.md）。

§6.5 で音量に反映する（依頼者の決定）。spec §9 の未決事項 2 を解決済みにする。

## 8. 依存の方向

- `conv` は `sequencer` の `parseMml` と定数（`TICKS_PER_QUARTER` など）だけを使う（spec §1 のとおり）。`sequencer` への変更は §6.10 のトラック名だけ。`runtime`・`engine` には依存しない。
- `conv` はゲームへコピーしない（`npm run export:runtime` の対象外）。

## 9. 確かめ方（実装側）

- Vitest：テストで小さな SMF のバイト列を組み立て、変換結果を確かめる。
  - 変換した MML を `parseMml` に通し、ノートの tick・ノート番号・長さ・音量・パン・ベンドが、SMF から期待する値と一致すること。
  - フォーマット 0・1、分解能 480・96 など、ベロシティ 0 のノートオン、同じ音の重なり、和音の分割、ドラムの割り当てと同時打ちの分割、ループのマーカー（あり・なし・片方だけ）、3 連符、量子化で 0 になるノート、30 トラックを超える場合、±1200 を超えるベンド、RPN 0、テンポの変化、持続中のノートの途中のテンポ・音量の変化。
- `parseMml`：`R1` などのトラック名が通り、ドラムトラックの規則が効くこと、`R0`・`R01` がエラーのままであること。
- 依頼者の Domino の曲：依頼者からもらえれば、変換して `parseMml` が通ることを確かめる（リポジトリには入れない。私の判断）。
- 完了を報告する前に `npm test`、`npm run build`、`npm run check:browser` を通す（CLAUDE.md）。
